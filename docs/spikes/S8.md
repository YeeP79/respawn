---

## Spec

**Question:** When two services share a base image but push to different ECR repositories, is the base stored once or twice?

**Pass bar:** A measured storage figure for two existing repositories that share a base layer. Pass = a number, either way — this spike cannot fail, only inform.

**This decides:** How much a variant actually costs, and therefore how hard to push on collapsing branches into knobs. If layers are shared the cost argument evaporates; if not, it is real and recurring.

**Why this spike exists:** The proposed structure argues for knobs over branches partly on registry cost, using arithmetic (15.6 GB × N services) that assumes no cross-repository sharing. That assumption was stated in the dossier and flagged as unmeasured. An argument resting on an unmeasured number should not be used to make a structural decision.

---

## Prior art

Searched 2026-08-28, **after** measuring — and it changed the answer, which is
the argument for searching first rather than last.

- [Amazon ECR now supports cross-repository layer sharing](https://aws.amazon.com/about-aws/whats-new/2026/01/amazon-ecr-cross-repository-layer-sharing) — the decisive source. **January 2026**: ECR gained blob mounting, storing each unique layer once per *registry* rather than once per *repository*. Before that, a base layer shared by 50 repositories was stored 50 times.
- [Amazon ECR pricing](https://aws.amazon.com/ecr/pricing) — $0.10 per GB-month.
- Commentary on the change — **skimmed** — consistently notes it is a **registry-level setting you enable**, not automatic on existing registries.

The last point is the one that mattered: the feature exists, so the honest
question stopped being "does ECR deduplicate" and became "is it switched on
here".

---

## What was actually done

Three passes, because the first two did not settle it.

**1 — Do the repositories actually share layers?** Resolved each repo's newest
image through its multi-arch index to the amd64 manifest, and compared layer
digests across the three cs16 variants.

**2 — Which model does the bill match?** Enumerated every layer in every
repository and computed two totals: the sum of per-repository layers (what a
no-deduplication registry stores) and the registry-wide unique set (what a
deduplicating one stores). Pulled actual billed `TimedStorage-ByteHrs` from Cost
Explorer for the preceding week and converted GB-hours to GB.

**3 — Ask the registry directly.** `aws ecr get-account-setting`.

---

## Result

**The sharing is real and substantial.** The three cs16 variants sit in three
separate repositories and hold **19 byte-identical layers, 636.7 MB**, in common:

```
respawn/cs16      21 layers   636.7 MB
respawn/cs16-dm   27 layers   643.0 MB
respawn/cs16-kz   34 layers   757.4 MB

cs16 ∩ cs16-dm  = 19 shared layers, 636.7 MB identical
cs16 ∩ cs16-kz  = 19 shared layers, 636.7 MB identical
cs16-dm ∩ cs16-kz = 19 shared layers, 636.7 MB identical
```

Across the whole registry as it stands: **3.59 GB** if duplicated,
**2.28 GB** if deduplicated — **1.30 GB** at stake.

**The billing comparison failed to discriminate, and is recorded as a failed
method rather than deleted.** Billed storage was a steady **1.86 GB** across
Aug 23-27, but that window predates the day's `cs16-kz` pushes. Recomputing both
models with today's 16 images excluded collapsed the gap:

```
Model A — no cross-repo dedup : 2.06 GB
Model B — dedup               : 2.03 GB
AWS actually billed           : 1.86 GB
```

0.03 GB apart. Nothing can be concluded from that, and treating the 0.17 vs 0.20
GB residual as a signal would have been reading noise.

**The registry answers directly:**

```
$ aws ecr get-account-setting --name BLOB_MOUNTING
{ "name": "BLOB_MOUNTING", "value": "DISABLED" }
```

---

## Answer

**Today, yes — layers are duplicated across repositories, and we pay for it.**
Cross-repository layer sharing exists as of January 2026 but is a registry
setting, and on this account `BLOB_MOUNTING` is **DISABLED**. So the current fleet
carries **1.30 GB** of duplicated layers that are separately billed.

**But the number that decides anything is the absolute one: the entire registry
is billed at ~1.86 GB, which is about 19 cents a month.** The duplication portion
is roughly 13 cents. At that magnitude, registry storage is not an argument for
or against anything.

**And it is a one-setting fix.** Enabling `BLOB_MOUNTING` makes ECR store each
unique layer once per registry, which would eliminate the duplication and speed
up pushes — the deploy path already spends real time on layer upload.

---

## Consequences

**Retracts an argument the proposed L4D2 structure was leaning on.** The dossier
used registry cost as a reason to prefer a knob over a branch, on arithmetic
(15.6 GB × N services) that was explicitly flagged as unmeasured. The arithmetic
was directionally right — layers really are duplicated — and the conclusion was
still wrong, because the absolute figure is cents. **Branch-vs-knob should be
decided on client experience and maintenance burden alone**, which is what the
rule in that document already says. The cost sentence has been corrected.

**Produces one concrete action, not yet taken:** enabling `BLOB_MOUNTING` on the
registry. It is account-wide, so it wants a human decision rather than a spike
doing it unilaterally. Benefit is small in money and real in push time.

**A method worth reusing, and one worth not.** Comparing computed models against
Cost Explorer was the right instinct and produced nothing usable here, because
the fleet changed inside the measurement window — the models converged to within
0.03 GB and any conclusion would have been noise. Asking the service what its
own setting is took one call and was decisive. Prefer the direct question.

**No spike spawned.**
