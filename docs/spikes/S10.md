# S10 — Does a server-side VScript addon work without the client installing it?

**Status:** ✅ Pass — with a required deploy step nobody would have guessed
**Blocking:** ~~Yes~~ — **answered 2026-08-30.** Briefly downgraded when a SourceMod alternative was found, then re-raised once the requirement was understood properly. ## Spec

**Question:** With a VScript-only addon VPK installed on the server and absent from the client, does the addon take effect for that player?

**Pass bar:** Left 4 Bots 2 (Workshop `3022416274`) + Left4Lib in the server's `addons/`, a client with neither, joining and observing bot behaviour that vanilla AI does not produce — bots defibbing a dead player, scavenging gascans, or responding to an order. Pass = the addon's behaviour is observable to a client that does not have it. Fail = the player joins and bots behave vanilla, or the join fails.

**This decides:** Whether Left 4 Bots — and with it the whole squad-commander direction — can be in the base. Also, generally, whether VScript addons are base-eligible. If they work server-side, Left 4 Bots goes in the base and improves the common case (these servers are usually one or two humans plus bots) at zero cost to joiners. If not, it is a branch with a client ritual, and the same applies to every other VScript addon.

**Why this spike exists:** S4 and S9 measured, three ways, that a client cannot be sent a **map** — it connects, is admitted as a player, then dies on `Host_Error: CMapLoadHelper::Init`, and `sv_downloadurl` produces zero HTTP requests. It is tempting to generalise that to "any VPK requires client install", and **that generalisation is not supported**. A campaign VPK carries `.bsp` files the client's renderer must load; a VScript addon carries `.nut` files the server executes. Those are different mechanisms and only one of them was measured.

Getting this wrong is expensive in both directions: marking it `client-side` when it is not costs the base its best bot improvement for no reason, and marking it base when it is not ships a server whose advertised behaviour silently does not happen for anyone.

## What was actually done

Fetched both Workshop items anonymously — no account, and the operator's own
subscriptions untouched:

```
steamcmd +login anonymous +workshop_download_item 550 3022416274   # Left 4 Bots 2, 703,335 B
steamcmd +login anonymous +workshop_download_item 550 2634208272   # Left 4 Lib,   201,405 B
```

**The VPK contents are themselves a finding.** Left 4 Bots is **70 `.nut` files under
`scripts/`**, plus a thumbnail and one txt. Zero models, materials, maps or sounds —
nothing a client could need to *render*. That is not proof of server-side operation,
but it does mean the S4 mechanism (a client failing to load a `.bsp` it does not
have) cannot apply here: there is no renderable content to be missing.

Server: the S1 image with both VPKs bind-mounted into `/addons/`, `c1m1_hotel` coop
(a stock map, so no campaign confound), `sv_allow_lobby_connect_only 0`, addressed
on the container bridge IP per S4 Trap 3.

Client: joined with **neither** addon (verified absent before the run), then — for
the control — with both hand-installed into `addons/`.

Command channels attempted, in both configurations: chat (`!l4b help`,
`!l4b bots warp`, and the prefix-less form), the client console
(`scripted_user_func l4b,bots,wait`), and the in-game vocalizer radial.

## Result

### Confirmed: the addon loads and runs fully server-side

With the client holding nothing:

```
[L4B][INFO] Initializing for game mode: coop (coop) - map name: c1m1_hotel - difficulty: normal
[L4B][INFO] Including coop/l4b_c1m1_hotel automation script...
[L4B][INFO] Loaded 13 mappings          (the vocalizer -> order table)
[L4B][INFO] Config file 'left4bots2/cfg/weapons/rochelle.txt' ... recreated
[L4L][INFO] HooksHub hooks OK
[L4L][INFO] Player joined: YeeP
>>> Loading addon script .../left4lib.vpk/scripts/vscripts/director_base_addon.nut
```

845 `[L4B]` log lines. It initialised for the specific map, ran that map's
automation script, wrote per-survivor weapon-preference files, installed its hooks,
and **registered the joining player by name and SteamID** — all with a client that
had never seen the addon. Whatever else is true, the addon is not inert without the
client.

### Not established: whether the command surface works

One clean capture exists, from the no-client configuration. The chat line reached
the server verbatim and produced no reaction:

```
"YeeP<2><STEAM_1:1:14886575><Survivor><Gambler><ALIVE><100+0>..." say "!l4b help"
```

Every later observation is **void**, for a reason worth recording in full.

### The instrument failed, and it was not noticed for four readings

Server logging was enabled with `log on` + `sv_logecho 1`, which worked — the chat
line above and the operator's own rcon calls appeared on stdout. It then **stopped
mid-session**: the container's last log entry was the bots spawning at 20:03:43,
while the server stayed alive and answered rcon for several minutes afterwards.
`sv_logecho` was re-issued and did not restore it.

So four consecutive "no reaction" readings — including every reading in the
control configuration — were taken against a dead readout. They are not evidence of
anything. In particular **the control never produced a comparable measurement**, so
there is no matched pair, which is the exact standard S4 was held to.

## Answer — REVISED after the permission fix

**PASS.** A VScript addon runs *and is fully drivable* on a dedicated server with no
client-side copy of anything required for the server's own operation. Left 4 Bots
belongs in the base.

**The blocker was a permission system, not the client.** `left4lib_users.nut`:

```squirrel
if (Director.IsSinglePlayerGame())
{
    return L4U_LEVEL.Admin;      // listen server: the player IS admin, automatically
}
...
return GetSteamIDUserLevel(steamid);   // dedicated: User(0) unless listed
```

On a listen server — which is how the Workshop's entire audience plays — every player
is silently promoted to `Admin`. On a dedicated server the same player is `User` (0),
and every command is dropped **without a message, a log line, or any other signal**.
Chat still works, because L4B's `hi` responder needs no level. Bots are still tracked.
The order HUD still renders. Only the orders vanish.

**The fix is one file**, `ems/left4lib/cfg/admins.txt`, one line per admin:

```
STEAM_1:1:14886575 //YeeP
```

Read at init, so it needs a restart. `l4u add <player> a` exists but cannot bootstrap
— it requires being admin already, so on a dedicated server the file must be written
directly.

Verified live: with the SteamID added, `!l4b bots wait` was accepted and the bots
obeyed. Before it, byte-identical everything else, they ignored it.

### What made this take four hours

Every symptom pointed at the client, and none of them were about the client:

| Symptom | What we inferred | What was true |
|---|---|---|
| Commands ignored, client had nothing | client must need the addon | permission level 0 |
| Still ignored with client subscribed | maybe our syntax is wrong | still level 0 |
| Chat visible, commands not | chat hook broken? | chat needs no level |

The **silent** rejection is the whole story. A one-line "you are not an admin" would
have ended this in five minutes, and its absence is worth remembering as a class of
bug: a permission check whose failure mode is indistinguishable from a dead feature.

What holds: **a VScript addon does load, initialise and run on a dedicated server
with no client-side copy.** That alone narrows the S4 finding usefully — "a client
cannot be sent a map" does not generalise to "any VPK requires client install",
which was the fear that spawned this spike.

What does not hold: any claim about the **command surface**. It was never measured
in a state where the measurement could be trusted. The single clean reading is one
data point in one configuration with nothing to compare it against.

**Do not record this as "L4B needs the client".** That was the working hypothesis
for most of the session and the evidence does not support it — the same evidence is
equally consistent with a broken readout, and the one thing that would separate them
(the control) is the part that was never validly measured.

## Consequences — REVISED

**Left 4 Bots is unblocked and belongs in the base.** `mods/mods-bots.txt` should be
flipped: L4B active, the Bot AI Improver dropped (they conflict, and L4B is the one
with the order vocabulary the agent ambitions rest on).

**A new deploy requirement, and it generalises.** Any Left4Lib-based addon needs
`ems/left4lib/cfg/admins.txt` provisioned per server, listing the SteamIDs allowed to
command bots. That is:

- **a config file only the game container can write**, exactly like the Valheim rcon
  password (`apps/valheim/respawn-rcon-config.sh`) — same shape, same reason
- **not secret**, so unlike the rcon password it can be a plain `GAME_ENV_` value
  rendered into the file by a shim
- **fail-silent if missing**, which is the dangerous part: the server comes up
  healthy, the addon loads, and nobody can drive it. A preflight check belongs here

**§3 and §3b of `docs/l4d2-agent-ambitions.md` are unblocked** — the squad-commander
direction and the vocalizer→order idea both rest on L4B's order surface, which is now
demonstrated working on the deployment target.

**Still open:** whether *rcon* (as `Console<0>`, no player) can drive orders. It could
not before the permission fix, but that test was run at level 0 like everything else
and is worth re-running. If it still cannot, the agent needs a bridge plugin — the
`respawn-director` idea in §4.

### Original (superseded) reading, kept deliberately

The section below recorded S10 as inconclusive after the first attempt, when the log
readout failed mid-session. It is left in place because the reasoning it contains —
about not trusting an unverified instrument — is what eventually produced the answer.

**S10 stays open.** `mods/mods-bots.txt` keeps Left 4 Bots as the intended choice,
blocked, exactly as it was.

The expensive parts are done and the re-run is cheap — both VPKs are cached in
`lab/s10-vscript/` (892 KB), the rig is the S4 recipe, and the traps are known.

**Three things the re-run must do differently:**

1. **Verify the readout before every observation, not after.** The failure here was
   not the logging breaking; it was four readings taken without checking it still
   worked. A one-line probe (`rcon status` appearing on stdout) before each test
   would have caught it immediately.
2. **Do not test with a command whose only output is text.** `!l4b help` prints to a
   destination neither party had verified, so "nothing happened" was uninterpretable
   from the start. Use an order with a physical effect — `bots warp` teleports every
   bot to the caller, which cannot be misread.
3. **Consider a listen server as the control instead.** L4B is distributed through
   the Workshop for players, where the host *is* the client. If it works there and
   not on a dedicated server, that is the real answer and it is reachable without
   any of this rigging.

**Method note worth keeping.** The habit that produced the good results today —
S4's matched pair, the muted-director smoker — is *change one thing and verify the
observation channel*. This spike drifted away from it under time pressure: the
director was muted mid-run, bots were deleted and re-added with `nb_delete_all`,
`sv_cheats` was toggled, and the client addon was installed, all inside one session,
with the readout failing somewhere in the middle. The result is a session's work
that answered half a question.
