## Spec

**Question:** S11 found `sv_maxplayers` present (max 31), `sv_removehumanlimit` absent,
and **L4DToolZ missing from `meta list`** — "something provides half the surface", with
S5's `oldlinux` finding named as the first suspect. Is it half-loaded, and does the cap
actually move?

**Pass bar:** Name what provides `sv_maxplayers`, and show whether the slot count can be
raised. Fail = the provider stays unidentified, or the cvar exists and does nothing.

**This decides:** Whether a big-coop variant is buildable on this stack.

## Result

### L4DToolZ is loaded. `meta list` is the wrong list.

```
plugin_print
  Loaded plugins:
  0:  "L4DToolZ v2.4.3, https://github.com/lakwsh/l4dtoolz"
  1:  "Metamod:Source 2.0.0-dev+1380"
```

The pack registers it through `addons/l4dtoolz.vdf` → the **engine's** server-plugin
loader, the same layer Metamod itself loads at — not through `addons/metamod/*.vdf` or
`metaplugins.ini`. So it sits *beside* Metamod rather than inside it, and `meta list`
correctly does not show it.

**Nothing was half-loaded and the `oldlinux` suspicion was misplaced.** S5's failure had
a loud symptom (`meta list` showing `[01] <ERROR>`); this had none, because there was
nothing wrong. The reading was taken from a list that does not cover the layer the plugin
was on — the same class of error as S10's dead log channel, and it cost S11 a "do not
build on this" conclusion that was not true.

`plugin_print` is the check. `meta list` alone cannot tell "absent" from "loaded one
layer up".

### `sv_removehumanlimit` does not exist, on either build tested

S5 measured it absent on Satanic-Spirit **2.2.0**; it is absent on lakwsh **2.4.3** here.
`lakwsh/l4dtoolz`'s own README documents `sv_maxplayers`, `sv_force_unreserved` and the
lobby-cookie calls, and no human-limit cvar at all. The community guides listing it
describe a build **neither** of these is, and its job is done by `sv_maxplayers`, whose
own help text is `- Max human players`.

### The cap moves, live, with no restart

```
                              status
sv_maxplayers  4  (default)   0 humans, 0 bots (4 max)
sv_maxplayers 12              0 humans, 0 bots (12 max)
sv_visiblemaxplayers 10       0 humans, 0 bots (10 max)     advertised count only
sv_maxplayers 40              clamped silently to 31
sv_setmax 31                  [L4DToolZ] maxplayers set to 31
                              0 humans, 0 bots (31 max)
```

### Four cvars, and they are not interchangeable

| cvar | what it controls | range |
|---|---|---|
| `sv_setmax` | engine max **clients** — the hard ceiling | 18–32, default **18** |
| `sv_maxplayers` | max **human** players; `-1` disables and restores the stock check | -1–31 |
| `sv_visiblemaxplayers` | the slot count **advertised** to browsers, nothing else | -1–… |
| `sv_force_unreserved` | refuse lobby matchmaking; also zeroes `sv_allow_lobby_connect_only` | 0/1 |

**`sv_setmax` defaults to 18 and is the real ceiling.** `sv_maxplayers` accepts up to 31,
so asking for more than 18 without raising `sv_setmax` is a request the engine cannot
honour. lakwsh's README says to pass `+sv_setmax 31` at launch; **measured, it also works
live over rcon**, which the README does not say.

**31, not 32.** The README's reason is explicit: above 31 crashes since The Last Stand
update. S5 saw max 32 on 2.2.0 — the newer build lowered the ceiling deliberately, so
this is not a version quirk to normalise away.

---

## Answer

**PASS.** The machinery is fully loaded and fully functional: 4 → 31 slots over rcon with
no restart, and every cvar in the set behaves as documented except `sv_removehumanlimit`,
which does not exist and was never needed.

---

## Consequences

**1. S11's finding 2 is withdrawn.** A big-coop variant is buildable on this stack; the
blocker was an observation taken from the wrong list.

**2. `plugin_print` belongs beside `meta list` and `sm plugins list`** in any "what is
loaded" check. Three loaders, three lists, and only one of them was being read.

**3. `sv_setmax` must be set, not assumed.** Raising `sv_maxplayers` to 24 on a server
whose `sv_setmax` is still 18 gives a server that reports 24 and cannot seat them — the
failure shows up as players failing to connect, nowhere near the cvar that caused it.

**4. `sv_removehumanlimit` comes out of the manifest comment.** It has never existed on
any build this project has run, and leaving it there sends the next person looking for a
cvar that was already measured absent twice.

**5. `sv_force_unreserved` interacts with `sv_allow_lobby_connect_only`**, which the fleet
docs already flag as a joinability trap — turning one on silently changes the other.

**No spike spawned.** S6 (what the fifth player must do) is untouched: this measured the
server side, and connecting five real humans still needs five real humans.
