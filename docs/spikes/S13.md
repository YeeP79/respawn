# S13 — Accelerator: fix the GLIBCXX mismatch, or drop it?

**Status:** ✅ Pass — fixed, with a caveat about what "fixed" was shown to mean
**Blocking:** No, but it decides whether the crash reporter ships
**Spawned by:** S11 finding 1
**Needs:** docker
**Run by:** Claude
**Date run:** 2026-08-30
**Commit / branch:** `1aef1d5` / `main`, image `l4d2-acc:s13`

---

## Spec

**Question:** Accelerator — the crash reporter — fails to load on `left4devops/l4d2`:

```
[SM] Unable to load extension "accelerator.ext":
     bin/libstdc++.so.6: version `GLIBCXX_3.4.21' not found
```

Can it be made to load, or must it be dropped?

**Pass bar:** Either it loads **and the rest of the stack is unharmed**, or it is removed
from the manifest with a reason good enough that nobody re-adds it.

**This decides:** Whether the modded variant has crash reporting at all. A crash reporter
that silently fails to load is a false assurance about the one thing nobody is watching,
so "ship it and hope" is not on the table.

## What was actually done

Every requirement read with `readelf -V`, not inferred from the error text — the error
names the *first* missing version, not the highest.

```
accelerator.ext.so needs   GLIBCXX_3.4.29 (GCC 11), GLIBC <= 2.34, and only GCC_3.0
game's bin/libstdc++.so.6  provides GLIBCXX <= 3.4.16   (a 2012-era GCC 4.7)
base image                 has NO other 32-bit libstdc++; LD_LIBRARY_PATH is ".:bin:"
                           so bin/ wins unconditionally
```

The gap is thirteen minor versions. **No older Accelerator build closes it** — 3.4.21 is
already GCC 5 (2015), so anything that works with SourceMod 1.12 is far above 3.4.16.
The library has to be replaced.

### Two measured dead ends, in order

**Replace `libstdc++` alone** — Rocky 9's own `libstdc++-11.5.0.i686` fits Accelerator
exactly (GLIBCXX_3.4.29, GLIBC ≤ 2.34):

```
Failed to open dedicated_srv.so
  (bin/libgcc_s.so.1: version `GCC_7.0.0' not found (required by bin/libstdc++.so.6))
```

Valve's bundled libgcc tops out at GCC_4.5.0. The two are a matched pair.

**Add Rocky's own `libgcc.i686`:**

```
Failed to open dedicated_srv.so
  (/lib/libc.so.6: version `GLIBC_2.35' not found (required by bin/libgcc_s.so.1))
```

**Rocky 9's i686 multilib pair does not work on Rocky 9.** `baseos` offers exactly one
`libgcc.i686` (11.5.0-14.el9) and it references `_dl_find_object@GLIBC_2.35` — a symbol
added in glibc 2.35 for stack unwinding — while RHEL 9 is pinned at glibc **2.34**. The
image has `glibc-2.34-168.el9_6.14.i686` installed and no newer 2.35 exists for el9 at
all, so this is not a version somebody forgot to update. Debian bookworm's `libgcc-s1`
12.2.0 was checked for the same reason and has the identical floor.

### What works

The GCC_7.0.0 requirement comes from the **replacement libstdc++**, not from Accelerator
— Accelerator itself wants only `GCC_3.0` from libgcc. So the pair that works is a libgcc
new enough to carry GCC_7.0.0 and old enough to predate glibc 2.35:

| | source | provides | needs |
|---|---|---|---|
| `libstdc++.so.6` | Rocky 9 `libstdc++-11.5.0-14.el9.i686` | GLIBCXX_3.4.29 | GLIBC ≤ 2.34, GCC_7.0.0 |
| `libgcc_s.so.1` | Debian bullseye `libgcc-s1_10.2.1-6_i386` | GCC_4.5.0/4.7.0/4.8.0/**7.0.0** | GLIBC ≤ **2.2.4** |

Both originals are kept beside the replacements as `*.valve`, so a rollback is one `mv`
and does not need the image rebuilt. The `.deb` is pinned by version **and sha256** —
a pool URL without a hash is exactly the moving target this session is elsewhere trying
to remove.

## Answer

**PASS — fixed.** Accelerator loads, all 13 extensions come up clean, and S12's whole
VScript order path still works.

**What this did NOT show:** that the swapped C++ runtime is stable under hours of load.
A C++ ABI problem surfaces as a crash, not as a boot failure, and the component being
installed is the crash reporter. The evidence here is a clean boot, a full stack, a
running round and a bot obeying an order — not a soak test. The `*.valve` originals stay
in the image precisely because that is the open question.

---

## Consequences

**1. Accelerator is re-enabled in `mods-stability.txt`**, with the library requirement
recorded next to it. It is not a plain "uncomment" — it only works on an image carrying
the swap, so the entry names it.

**2. The swap belongs in the variant Dockerfile**, not in a shared base: it is two files
and a pinned `.deb`, and every service that does not run Accelerator is better off on
Valve's own libraries.

**3. Do not "simplify" this to Rocky's own multilib.** The obvious cleanup — drop the
Debian dependency, use `libgcc.i686` from the same distro as the libstdc++ — is the
configuration that was measured and does not boot. The comment in the Dockerfile says so.

**4. Watch the first crash.** The value of the whole change is a symbolicated report the
next time a task dies unexplained; if the swap itself is what kills it, `*.valve` is the
first thing to put back.

**No spike spawned.**
