# S5 — Is the slot machinery inert at four players?

**Status:** ✅ Pass
**Blocking:** No — but it decides base membership, and therefore how many images exist.
**Spawned by:** —
**Needs:** Local docker only. No AWS.
**Run by:** Claude (paired)
**Date run:** 2026-08-28
**Commit / branch:** `feat/goldsrc-mod-variants` · `lab/s5-slot-machinery/`

---

## Spec

**Question:** With L4DToolz, MultiSlots and the companion fixes installed but `sv_maxplayers` left at its default, does the server behave exactly as one without them?

**Pass bar:** Two builds — base+slot-machinery and base-only — boot the same map with the same config. Both report 4 slots to A2S, both load with no errors, and the plugin-list diff is the only difference. **Any behavioural difference at 4 players is a fail.**

**This decides:** Whether player count is an `.env` knob on one image, or a second 15.6 GB image. That is the single biggest structural choice in the proposed layout.

**Why this spike exists:** The proposed base puts L4DToolz in the template on the strength of its documented default (`sv_maxplayers -1` disables it and falls back to the standard check). If that is true, player count stops being a build difference. If it is not — if the plugin changes lobby behaviour or slot reporting merely by being loaded — the whole slot group moves to the big-coop branch and the base shrinks.

## Prior art

Searched 2026-08-28.

- [L4DToolz](https://github.com/Satanic-Spirit/L4DToolz) and [accelerator74/l4dtoolz](https://github.com/accelerator74/l4dtoolz) — **skimmed**. Documented cvars: `sv_maxplayers` (0–32, **-1 to disable and use the standard check**), `sv_visiblemaxplayers`, `sv_removehumanlimit`, `sv_force_unreserved`. The `-1` default is the entire basis for the proposal and has not been exercised.
- Left4DHooks 1.168 thread — **read in full** — routes slot changes to L4DToolz explicitly, confirming there is no alternative to evaluate.

Not found: anyone reporting on L4DToolz's behaviour when loaded but disabled. The plugins most likely to break on a Valve update are exactly these, which is the argument on the other side.

## What was actually done

Built `lab/s5-slot-machinery/Dockerfile` — the S1 base plus **L4DToolz only**, so
any difference at four players is attributable to that one addition. Booted both
images side by side on identical arguments and compared load errors, `meta list`,
`sm plugins list`, A2S slot counts and `status`.

Then tested the knob itself: raised `sv_maxplayers` on the slot image while
leaving the base untouched as a live control.

---

## Result

**First attempt failed to load, and the reason is worth keeping:**

```
[META] Failed to load plugin addons/l4dtoolz/l4dtoolz_mm:
  /lib/libc.so.6: version `GLIBC_2.38' not found
```

The base image carries **glibc 2.34**; the release's plain `linux` asset is built
against 2.38. The release also ships an **`oldlinux`** asset, which is what this
image needs. The failure mode is instructive: the server booted perfectly and
simply had no slot support — `meta list` showed `[01] <ERROR>` and nothing else
was wrong. That is precisely the shape of bug this spike exists to catch.

**With the `oldlinux` build — clean, and identical to base at defaults:**

```
                       base            base + L4DToolz
load errors            0               0
meta list              5 plugins       6 plugins  ([01] L4DToolZ 2.2.0)
sm plugins list        18              18   (byte-identical)
A2S                    players=0/4     players=0/4
status                 (4 max)         (4 max)
```

Its own cvars sit at the documented disabled default:

```
"sv_maxplayers"        = "-1"  min. -1.0  max. 32.0
"sv_visiblemaxplayers" = "-1"
```

**The knob works, live, with no restart:**

```
sv_maxplayers 8   ->  slot image : players=0/8
                      base image : players=0/4   (untouched control)
```

**One documentation correction:** `sv_removehumanlimit`, which the community
guides list, returns `Unknown command` on 2.2.0. Those guides describe an older
build.

---

## Answer

**PASS.** With `sv_maxplayers` at its default, a server carrying L4DToolz is
indistinguishable from one without it: same slot count, same SourceMod plugin
list, zero load errors. The only difference is one extra entry in `meta list`.

And it is not merely inert — it is inert *and* immediately useful: raising
`sv_maxplayers` over rcon changed the advertised slots with no restart, while the
control server stayed at four.

---

## Consequences

**L4DToolz goes in the base**, and player count becomes an `.env` knob rather
than a second image. That was the proposal; it is now measured rather than
assumed. Because the cvar takes effect live, it is arguably better than an
`.env` knob — a running server can be resized over rcon, which the MCP could
expose directly.

**The `oldlinux` build is mandatory and must be pinned as such.** Anyone
switching to the plain `linux` asset gets a server that boots fine and silently
lacks slot support. The Dockerfile records the exact error.

**Reduces what S6 has to answer.** S6 asks what the fifth player must do; the
server-side half of big-coop is now known to work from a single cvar, so S6 is
purely about the client experience.

**No spike spawned.**
