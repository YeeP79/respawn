## Spec

**Question:** After adding the base mod stack, how large is the image, and what `ephemeralStorage` value does a task actually need?

**Pass bar:** A measured image size for base-only and base+one-campaign, plus a chosen `ephemeralStorage` figure with stated headroom for the writable layer. Pass = the numbers exist and the chosen value is justified by them rather than rounded up hopefully.

**This decides:** The `ephemeralStorage` config key: its validation range, its default, and whether campaigns force a per-service override.

**Why this spike exists:** `ephemeralStorage` appears **nowhere** in the CDK or the config loader (measured 2026-08-28), while the base image measures **15.6 GB** against Fargate's 20 GiB default. Image layers count against that allocation, leaving roughly 4 GB before a single plugin. Nothing can deploy until this is both sized and wired.

## Prior art

Searched 2026-08-28.

- [AWS Fargate FAQ](https://aws.amazon.com/fargate/faqs/) and [Increasing disk space on ECS Fargate](https://repost.aws/knowledge-center/ecs-fargate-increase-disk-space) — **read in full**. Default 20 GiB, configurable to **200 GiB** on ECS; image layers consume the same allocation. So the ceiling is not the problem and the gap is entirely ours.
- `docker images` on this machine — **measured**: `left4devops/l4d2:latest` = **15.6 GB**.
- The sidecar-budget check added to `loader.ts` on 2026-08-28 is the pattern to copy: a validated `.env` key that fails fast with a message naming the shortfall, with specs.

## What was actually done

Measured the image four ways, because the first two disagreed by 50% and the
answer decides whether a CDK change is a prerequisite:

```
docker images                   15.6 GB (stock) / 15.9 GB (modded)
docker history, summed layers   10.33 GB
du -sx / inside the container   10.36 GB
docker export | wc -c           10.51 GB
```

Then checked whether the discrepancy was **delete-in-a-later-layer bloat** —
where overlay2 keeps a file a later layer removes, making real disk usage exceed
the merged filesystem view. It is not:

```
10.1GB   RUN |3 GAME_ID=222860 INSTALL_DIR=l4d2 ...   <- one layer, the game
169MB    KIWI 10.2.24
59.7MB   RUN /bin/sh -c ./as-root.sh
```

The game arrives in a single layer and nothing later deletes it, so the merged
view and the on-disk total coincide. Also measured the running container's
writable layer.

---

## Result

**Three independent measures agree at ~10.4 GB; `docker images` is the outlier
and is wrong here.**

```
stock left4devops/l4d2    du -sx /  = 10.36 GB   (docker images claims 15.6 GB)
modded (base stack)       du -sx /  = 10.36 GB   (docker images claims 15.9 GB)
mod stack contribution    /addons   =  221 MB
writable layer, running               ~115 kB
```

**Fargate arithmetic, corrected:**

```
modded image extracted : 10.5 GB  =  9.8 GiB
Fargate default        :            20.0 GiB
headroom               :            10.2 GiB
```

---

## Answer

**PASS — and the premise this spike was built on was wrong.**

The image is **~10.4 GB extracted, not 15.6 GB**. Fargate's 20 GiB default leaves
about **10 GiB of headroom**, not the ~4 GB recorded in the L4D2 dossier and in
this spike's own "why this exists". The whole mod stack adds **221 MB**, and the
writable layer during a run is negligible.

So **`ephemeralStorage` is not a prerequisite for a modded L4D2 service.** It can
deploy on the default today.

It is still not configurable, and that remains a real gap — a campaign-heavy
variant is the case that would need it, since roughly 10 GiB of headroom is
generous but finite. The gap simply stops being a blocker and becomes a
follow-on.

---

## Consequences

**Removes a blocker.** The dossier listed ephemeral storage as one of two things
that had to be fixed before anything L4D2 could ship. It does not. The `.env`
key and loader validation are still worth adding — a per-service knob is the
right shape, and campaigns will want it — but they no longer gate the first
deploy.

**Corrects a number in three places**: the dossier's status card and
infrastructure section, and this spike's own premise. All three came from
`docker images`, which for this image reports 50% high.

**A method note worth keeping.** `docker images` is the number everyone quotes
and it was the wrong one. It disagreed with three other measures, and the way to
tell which to trust was to check *why* they could legitimately differ — overlay2
retains files deleted by later layers, so a merged-filesystem view can understate
real disk. Inspecting the layer structure ruled that out and made the three-way
agreement meaningful rather than coincidental. **Do not size infrastructure from
`docker images` alone.**

**No spike spawned.**
