# S1 — Does the full mod stack build and load together?

**Status:** ✅ Pass
**Blocking:** **Yes — first.** Every other spike except S8 needs a running modded server.
**Spawned by:** —
**Needs:** Local docker only. No AWS, no cost.
**Run by:** Claude (paired)
**Date run:** 2026-08-28
**Commit / branch:** `feat/goldsrc-mod-variants` · build recipe in `lab/s1-modded-image/`

---

## Spec

**Question:** Can one derived image carry MetaMod:Source, SourceMod, Left4DHooks, All4Dead2 and Stripper:Source, and boot to a playable map with all of them loaded?

**Pass bar:** `meta list` shows MetaMod and SourceMod loaded; `sm plugins list` shows Left4DHooks, All4Dead2 and Stripper running; the server reaches a map and answers A2S; **zero** plugin load errors and zero `[SM] Unable to load` lines in the boot log.

**This decides:** Whether the proposed base template is real, and what actually belongs in it. A component that will not load here does not get to be in the base.

**Why this spike exists:** The whole base-and-branches structure assumes these five coexist. Nothing has compiled or loaded them together — the versions come from a third-party pack that tracks 2026 releases, not from a build we ran. L4D2 plugins break on Valve updates, so a stack that is individually current can still fail as a set.

## Prior art

Searched 2026-08-28.

- [Left 4 DHooks Direct 1.168 thread](https://forums.alliedmods.net/showthread.php?t=321696) — **read in full** (via Chrome; Cloudflare blocks automated fetching). v1.168 dated 18-Jun-2026, reports 2,297 servers. Detours dynamically, rescanning on map change, so an unused base install should be close to free. States outright: *"Player slots is unsupported. Use the L4DToolZ Metamod plugin."*
- [SNWCreations/l4d2-modded-server](https://github.com/SNWCreations/l4d2-modded-server) — **skimmed**. Pins SourceMod 1.12 / MetaMod:Source 2.0.0 and bundles this same set, which is the strongest evidence they coexist. Not verified by us.
- [How to make a L4D2 server with mods (2026)](https://moddingcommunity.com/blog/how-to-make-a-l4d2-server-with-mods/) — **read in full**. Gives the install paths (`plugins/` `.smx`, `gamedata/`, `extensions/` `.so`) and the `autoexec.cfg` vs `server.cfg` split.
- [left4devops/l4d2 image docs](https://github.com/Left4DevOps/l4d2-docker) — **read in full**. Reads custom content from `/addons/` and config from `/cfg/server.cfg`, so a derived image needs no entrypoint replacement.

Not found: anyone running this stack on Fargate, or in a container with a read-only game dir.

## What was actually done

Built `lab/s1-modded-image/Dockerfile` — a builder stage that assembles the addon
tree, and a final stage that layers it onto the upstream image. Everything is
pinned; `latest` would make a failed boot impossible to attribute.

| Component | Pinned at |
|---|---|
| MetaMod:Source | `2.0.0-git1410-linux` |
| SourceMod | `1.12.0-git7251-linux` |
| Stripper:Source | `1.2.2-hg82-linux` |
| Left4DHooks | commit `f90ae5e6` (2026-06-18, = the 1.168 thread post) |
| All4Dead2 | compiled from source at build time with `spcomp64` |

Two structural facts about the base image made this simpler than expected, both
read out of the image rather than assumed:

```
/home/louis/l4d2/left4dead2/addons -> /addons
/home/louis/l4d2/left4dead2/cfg    -> /cfg
```

All three tarballs are rooted at `addons/`, so they layer directly into `/addons`
with no path rewriting. All4Dead2 needs only stock SourceMod includes
(`sourcemod`, `sdktools`, `sdkhooks`, `adminmenu`), so it compiles with the
bundled compiler and pulls in no further dependency — and `spcomp64` exists, so
the builder needs no i386 libraries.

Build:

```
docker build -f lab/s1-modded-image/Dockerfile -t l4d2-base-spike:s1 lab/s1-modded-image
```

Boot, deliberately bypassing the image's own entrypoint (see Consequences):

```
docker run -d --name s1srv -p 27016:27015/udp -p 27016:27015/tcp \
  --entrypoint /bin/bash l4d2-base-spike:s1 -c \
  'cd /home/louis/l4d2 && ./srcds_run -game left4dead2 -console -norestart \
   -ip 0.0.0.0 -port 27015 +sv_lan 1 +rcon_password spikepw +maxplayers 4 +map c1m1_hotel'
```

Verified with `lab/srcds-rcon.py`, a minimal Source RCON client written for this
spike and reused by S2 and S3.

## Result

**First boot failed the bar with two load errors**, both recorded here because
the fix is now baked into the Dockerfile and the reasons are not obvious:

```
 failed to dlopen .../addons/metamod/bin/linux64/server.so
   error=... wrong ELF class: ELFCLASS64
Unable to load plugin "addons/metamod/bin/linux64/server"
[SM] Failed to load plugin "nextmap.smx": Nextmap is incompatible with this game.
```

The first is `metamod_x64.vdf`, which ships in the MetaMod tarball and points at
a 64-bit binary; L4D2's srcds is 32-bit. MetaMod still loaded via the 32-bit
`metamod.vdf`, so this was noise — but noise indistinguishable from a real
failure. The second is a stock SourceMod plugin that refuses this game. Both
files are now removed at build time.

**Second boot, after removing them — zero load errors.**

## Answer

**PASS.** All five components load together on a pinned stack, the server reaches
a playable map, A2S answers, and the boot log carries zero load errors — after
removing two files that ship in the upstream tarballs and are wrong for this
game.

One wording correction to the bar itself: it expected Stripper under
`sm plugins list`. Stripper is a **MetaMod** plugin, not a SourceMod one, so it
correctly appears under `meta list`. The bar was written from the research rather
than from the software; the requirement was met, the sentence was imprecise.

Left4DHooks self-reports **1.168**, matching the AlliedMods thread exactly — so
the version pinned by commit is the version documented, which was an assumption
when the Dockerfile was written and is now a measurement.

## Consequences

**The base template is real.** The proposed shared base is buildable, loads
clean, and costs ~0.3 GB over the stock image. Nothing in the L4D2 dossier's
structure is invalidated by this spike.

**Two build steps are now mandatory for any L4D2 image** and are documented in
the Dockerfile with the reasons: remove `addons/metamod_x64.vdf` and
`addons/sourcemod/plugins/nextmap.smx`. Neither is discoverable except by
reading a boot log.

**Three findings this spike was not looking for:**

1. **The upstream entrypoint runs `steamcmd +runscript update.txt` on every
   boot.** Every container start is a network-dependent game update before the
   server exists. That is a cold-start cost and a failure mode on Fargate that
   nothing in the current `apps/l4d2` config accounts for. This spike bypassed
   the entrypoint entirely, so it is untested rather than solved.

2. **The entrypoint puts the rcon password in argv**: it builds
   `+rcon_password "${RCON_PASSWORD}"` into the srcds command line. CLAUDE.md's
   own gotcha says secrets must never reach `CONTAINER_COMMAND` precisely
   because argv is visible in `ps` inside the container — and here the upstream
   image does it for us from an env var. **This feeds directly into S3**, which
   was only asking whether srcds *logs* the password; it should also ask whether
   the entrypoint *exposes* it.

3. **A2S on current srcds requires a challenge round trip.** Checked rather than
   assumed whether our idle-shutdown sidecar handles it: it does, at
   `apps/respawn/sidecar/idle-shutdown/players.py:217-222`. Recorded so nobody
   re-checks — `IDLE_CHECK_METHOD=a2s` is safe for this service.

**Unblocks S2, S3, S5 and S7**, all of which needed a modded server to exist.
S7 additionally now has half its answer for free: base+mods measures 15.9 GB,
leaving campaigns as the only thing that could move that number materially.

**No spike spawned.** Finding 2 widens S3's question rather than creating a new
one; S3's spec has been updated to cover it.
