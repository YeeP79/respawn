# S16 — Does the agent loop work with a real player?

**Status:** ✅ Pass, with four defects found and fixed
**Blocking:** No — but it is the first evidence any of this works for a human
**Spawned by:** the modded variant being deployable
**Needs:** docker + a game client
**Run by:** Claude, paired with YeeP on the client
**Date run:** 2026-08-31
**Commit / branch:** `a91eae8`..`b982031` / `main`, image `l4d2-modded:local`

---

## Spec

**Question:** Everything through S15 was measured with `CreateSurvivorBot` and rcon. Does
the loop — player presses a key → plugin captures intent → agent reads it → agent issues
an L4B order → bots obey — actually work with a person playing?

**Pass bar:** A human presses a bound key and the bots do the right thing, more than once,
for more than one kind of order.

**This decides:** Whether `respawn_director` is a working bridge or a set of parts that
each pass in isolation.

---

## Setup

Local, not AWS, and deliberately: "do the mods work" and "does it run on Fargate" are
different questions and only the second needs a deploy. `scripts/run-local.sh` runs the
**same image the deploy builds**, with the variant's own `GAME_ENV_*` mapped exactly as
`loader.ts` maps them. Iteration was seconds instead of a 16 GB push.

## Result

### The loop works

Four order types confirmed live:

| pressed | captured | mapped to | outcome |
|---|---|---|---|
| F3 `hold here` | position + aim | `wait` at the player's feet | bots park |
| F4 `move up` | position + aim | `goto` at the **aim point** | see below |
| F1 `regroup on me` | — | `follow` the player entity | bots close and hold station |
| F6 `heal me` | — | `heal`, destEnt = player | Coach walked over and used his medkit |

**The v3 premise is proven.** On `move up` the player stood at `1089 5584 2718` looking at
`208 5668 2732` — 880 units apart. After the order:

```
distance to where he was LOOKING    104,  77,  84
distance to where he was STANDING   839, 871, 810
```

All three went to the crosshair. v2 could not do this: it inherited whatever the
impersonated player was looking at when the order was *sent*, seconds later.

`@closest` also resolved server-side to a named bot, and `sm_rd_give` works.

### Four defects, all the same shape: a success reply for something that did not happen

**1. An order queued behind another reported `OK`.** L4B orders its queue by a fixed
priority table; `BotOrderAdd` does not replace a CurrentOrder whose priority is >= the new
one, it inserts *behind* it. Bots running `goto` (1) were sent `follow` (0) for "regroup on
me": the call answered OK and the bots kept walking away. Fixed by superseding by default
(`queue=1` opts back in) and reporting a queued order as `QUEUED`, not `OK`.

**2. Ambiguous bot names picked one silently.** Survivor names are not unique — a bot
spawned to replace a lost survivor **clones an existing one**, so the team ends up with two
Ellises and the game itself starts printing *"Ellis saved Ellis"*. `sm_rd_order Ellis`
matched the first, answered OK with `of=1`, and gave no hint the other existed. Name
addressing is the default path (`@closest` resolves to a name), so this would have
mis-addressed silently for ever. Now refused, naming both userids.

**3. `sm_rd_status` counted the other team.** It counted every fake client, so AI specials
showed up as orderable bots — reported `bots=5 (Coach, Ellis, Rochelle, Jockey, Hunter)` on
a server with two orderable survivors, one of the three named already gone.

**4. A `wait` order does not survive the bot being moved.** L4B freezes rather than steers.
Full analysis and the repair are in the `b982031` commit message; the repair itself took
four more silent failures to land (an undocumented `ExecVScriptCode` size ceiling, a
`scripts/vscripts/` index that is built at map load, `TIMER_FLAG_NO_MAPCHANGE` killing the
sweep at the first map change, and nothing reporting any of them).

---

## Answer

**PASS.** A person pressed keys and bots obeyed, across four order types, repeatedly. Every
defect found was in the plugin's *contract* — what it reports — rather than in the VScript
path S12 proved.

---

## Consequences

**1. "Success" is the thing to distrust in this codebase.** All four defects returned OK.
None threw. A convention worth keeping: a reply that cannot distinguish "done" from "queued
behind something", "one of several", or "the other team" is not a report.

**2. Test on a bot-only server, not the one somebody is playing.** Teleport experiments
during live play killed two survivors and left the session with duplicate characters.
Synthetic tests belong somewhere nobody is standing.

**3. Never test whether a command exists by running it.** Probing All4Dead2's twelve
commands for existence meant *executing* `a4d_panic_forever` and `a4d_continuous_bosses`,
which turned the player's game into a boss rush. `a4d_reset_to_defaults` — the command S11
kept AtomicStryker's fork for — undid it in one call.

**4. Read a netprop's meaning before trusting it.** `m_hMyWeapons` is not in HUD-slot order;
reading index 3 as "the medkit slot" produced a false failure and very nearly a filed bug
against `sm_rd_give`, which works.

**5. The agent cannot listen and measure at the same time.** Player presses were dropped
whenever the agent was mid-diagnosis, because polling the inbox and running a measurement
spend the same serial resource. `scripts/watch-inbox.sh` under the Monitor tool fixes this
properly: it polls server-side and pushes one event per message. That is what it was written
for and it should have been armed from the first minute.

**6. A duplicate survivor survives a chapter transition.** Predicted otherwise during the
session and measured wrong: the next level began with two Rochelles. The only fix is not
creating the duplicate — `CreateSurvivorBot()` clones rather than filling the empty slot.

**No spike spawned.** S6 (the fifth-player ritual) is still the only open one.
