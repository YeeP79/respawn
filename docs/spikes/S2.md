# S2 — Can the MCP drive Source rcon, and do All4Dead2's commands work over it?

**Status:** ✅ Pass
**Blocking:** **Yes** — the entire MCP control surface for L4D2 rests on this.
**Spawned by:** —
**Needs:** Local docker + an rcon client. No AWS.
**Run by:** Claude (paired)
**Date run:** 2026-08-28
**Commit / branch:** `feat/goldsrc-mod-variants` · image from `lab/s1-modded-image/`, client `lab/srcds-rcon.py`

---

## Spec

**Question:** With no admin identity configured, does an rcon-issued `a4d_force_tank` actually spawn a Tank — and does its output come back to the caller?

**Pass bar:** Over rcon, with `sv_cheats 0` and no entry in `admins.cfg`: `a4d_force_tank` spawns a Tank, `a4d_add_zombies` adds a horde, and `sm plugins list` returns readable output to the rcon caller. Pass requires **all three**; a command that runs but returns nothing is a partial.

**This decides:** Whether the director surface is real, and whether the base image must ship an `admins.cfg` with a root identity. It also decides how much of the manifest can be trusted before a human tests it.

**Why this spike exists:** All4Dead2 registers its 13 commands with `RegAdminCmd`, which enforces an admin flag. SourceMod documents console-issued commands as carrying console authority, which *should* satisfy that — but the two facts have never been put together on a live server, and if they do not meet, every director command in the manifest is dead on arrival.

## Prior art

Searched 2026-08-28.

- [all4dead2.sp](https://github.com/AtomicStryker/atomicstrykers-codedump/blob/master/customized/all4dead2.sp) — **read the registrations directly** (grepped `RegAdminCmd`/`CreateConVar` out of the source). 13 commands, 5 cvars. This is the source of the command list; it is not a claim from a description.
- [SourceMod admin commands wiki](https://wiki.alliedmods.net/Admin_commands_(sourcemod)) — **skimmed**. Notes rcon output is returned on SourceMod 1.4+, and that protected cvars need rcon access while `sv_cheats` needs cheat access.
- Left4DHooks' own admin commands (`sm_l4dd_detours`, `sm_l4dd_reload`, `sm_l4dd_unreserve`) explicitly require the **root flag** — a useful control: if those work over rcon, flag inheritance from the console is confirmed for All4Dead2 too.

Not found: a direct statement that `RegAdminCmd` commands are callable from rcon with no configured admin. This is the gap the spike exists to close.

## What was actually done

Booted the S1 image and confirmed **no admin identity exists** before testing
anything, since the whole question is whether one is needed:

```
admins_simple.ini : 0 non-comment lines
admins.cfg        : Admins { }   (empty; the BAILOPAN block is SourceMod's
                                  commented-out documentation example)
```

Read the plugin source first, which changed the test design. `a4d_force_tank`
does not spawn a Tank — it calls `StripAndChangeServerConVarBool`, which clears
`FCVAR_CHEAT`, sets `director_force_tank`, and restores the flag. That makes the
effect a **readable cvar** rather than an entity to hunt for.

Ran a control before the test, so a pass could not be confused with rcon simply
having cheat rights:

```
director_force_tank 1     # directly, over rcon
a4d_force_tank 1          # the same change, via the plugin
```

Then mapped every command's argument requirements by invoking each with none,
and traced the two implementation paths in source
(`StripAndChangeServerConVar*` vs `StripAndExecuteClientCommand`).

## Result

**Baseline:** `sv_cheats = 0`; every target cvar reports `game cheat`.

**Control — plain rcon cannot do it:**

```
----- director_force_tank 1 -----
Can't use cheat cvar director_force_tank in multiplayer, unless the server has
sv_cheats set to 1.
----- director_force_tank -----
"director_force_tank" = "0"
```

**Test — All4Dead2 can, from rcon, with no admin configured:**

```
----- a4d_force_tank 1 -----
[all4dead2.smx] [NOTICE]: (Console<0><Console><Console>) set director_force_tank to 1
[A4D] A tank is guaranteed to spawn this round
----- director_force_tank -----
"director_force_tank" = "1" ( def. "0" )
```

The identity in the log is the answer to the spike's question:
**`Console<0><Console><Console>`**.

**`a4d_add_zombies 20`** moved all three horde cvars by exactly the argument:

```
z_mega_mob_size      50 -> 70
z_mob_spawn_max_size 30 -> 50
z_mob_spawn_min_size 10 -> 30
```

**`a4d_reset_to_defaults`** restored every one of them plus the three director
booleans, in one command.

**Arguments are required on 9 of the 12 commands** — the bar assumed
`a4d_add_zombies` took none:

| Command | Arguments |
|---|---|
| `a4d_force_tank` · `a4d_force_witch` · `a4d_panic_forever` · `a4d_continuous_bosses` · `a4d_enable_notifications` | `<0\|1>` |
| `a4d_add_zombies` | `<0..99>` |
| `a4d_spawn_infected` | `<infected_type>` |
| `a4d_spawn_uinfected` | `<riot\|ceda\|clown\|mud\|roadcrew\|jimmy>` |
| `a4d_spawn_item` · `a4d_spawn_weapon` | `<item_type>` (one shared handler) |
| `a4d_force_panic` · `a4d_reset_to_defaults` | none |

**A first run of `a4d_force_panic` threw**, and the reason turned out not to be
what it looked like:

```
[SM] Exception reported: Client index 0 is invalid
[SM] Blaming: all4dead2.smx
[SM]   [0] FakeClientCommand

[SM]   [2] Line 872  ... Do_ForcePanic

Source shows line 872 already handles console by substituting

bots added it works:

```
----- a4d_force_panic -----
[A4D] The zombies are coming!
```

**Spawning is independently confirmed.** `a4d_spawn_infected hunter` reported
success, and the spawned Hunter then appeared in `status` as a live entity:

```

## Answer

**PASS, on all three legs.** `a4d_force_tank` changes the game with `sv_cheats 0`
and no configured admin; `a4d_add_zombies` does the same to the horde cvars; and
`sm plugins list` returns readable output to the rcon caller.

The specific thing the spike existed to resolve — whether `RegAdminCmd` would
refuse an unauthenticated caller — is answered by the plugin's own audit line:
rcon executes as **`Console<0>`**, which carries implicit authority. **No
`admins.cfg` entry is required**, and the base image does not need to ship one
for the MCP to work.

Worth recording that the commands are registered `ADMFLAG_CHEATS`, not
`ADMFLAG_ROOT` as assumed when the spike was written. It makes no difference to
the result — console satisfies both — but it means a *human* admin would need
the `n` flag, not `z`.

**Two corrections to earlier claims, both mine:**

1. **There are 12 commands, not 13.** `a4d_debug_teleport` is commented out at
   source line 94. The original count came from a grep that matched inside the
   comment — the same class of error as reading a description instead of the
   code, one level down.
2. `a4d_continuous_bosses` prints its usage as `a4d_always_force_bosses`, an
   internal name that is not the registered command. Cosmetic, but it would send
   anyone reading the usage string to a command that does not exist.

## Consequences

**The MCP director surface is real**, and the base image needs no admin
configuration to use it. All4Dead2 stays in the base, as the structure proposed.

**The 12 commands split into two classes, and the split is predictable from
source** — this is the finding that should shape the manifest:

- **Cvar path** (`StripAndChangeServerConVar*`): `force_tank`, `force_witch`,
  `panic_forever`, `continuous_bosses`, `add_zombies`, `enable_notifications`,
  `reset_to_defaults`. These work **always**, including on a completely empty
  server, because they only move a cvar.
- **Client-command path** (`StripAndExecuteClientCommand` → `FakeClientCommand`):
  `force_panic`, `spawn_infected`, `spawn_uinfected`, `spawn_item`,
  `spawn_weapon`. These need **at least one client present**; bots count. On an
  empty server they raise a logged SourceMod exception rather than failing
  quietly — which is the good failure mode, but the MCP should not offer them
  when nobody is connected.

That distinction matters more than it looks: a scale-to-zero server spends most
of its life empty, and half these commands are exactly what somebody would try
first on a server they just woke up.

**`a4d_reset_to_defaults` is the safety valve** the manifest should lean on — one
command restores all six cvars the others touch. It is the natural counterpart
to marking `panic_forever` and `continuous_bosses` `danger: true`.

**Invalidates the "13 commands" figure** in the L4D2 dossier and in this ledger's
S2 row; both corrected. The dossier's claim that the commands need no
`sv_cheats` is confirmed, with a control.

**Unblocks nothing further** — S3 and S5 were already unblocked by S1. No spike
spawned: the `force_panic` failure resolved to a documented condition rather than
an open question.

## Follow-up: corrected against a live human player (2026-08-30)

S2 was run entirely with **bots**, and its central claim — that five commands
"need at least one client present" — was inferred from source, not exercised with
a real player. During the S4 run a human was connected to the same mod stack, so
all twelve were re-tested. **Three of S2's conclusions above are wrong and are
corrected here rather than edited in place**, so the reasoning that produced them
stays visible.

### 1. Two commands can NEVER be driven by rcon — they are not "presence-gated"

With a human connected and `active`:

```
a4d_spawn_weapon rifle          -> Can not use this command from the console.
a4d_spawn_item first_aid_kit    -> Can not use this command from the console.
a4d_force_panic                 -> [A4D] The zombies are coming!
a4d_spawn_infected hunter       -> [A4D] A hunter has been spawned
a4d_spawn_uinfected clown       -> [A4D] A zombie has been spawned
```

So the "client-command path" splits again. `force_panic`, `spawn_infected` and
`spawn_uinfected` work once somebody is connected, exactly as S2 predicted. But
`spawn_item` and `spawn_weapon` refuse **regardless of population**, because they
route through `give`, which hard-refuses a console caller. What they need is not a
client *present* but a client *calling* — a crosshair to spawn at — and `Console<0>`
has no position. No number of players fixes that.

**Consequence:** the modded variant's manifest must **omit** these two, not gate
them on population. S2's advice ("the MCP should not offer them when nobody is
connected") would have shipped two commands that can never work, and whose failure
looks like a transient population problem.

### 2. `spawn_uinfected` is not map-gated

Predicted before the run that a clown on a campaign with no Dark Carnival content
would silently fall back to a common infected. **Wrong** — a clown spawned on
"Time to Die" and the player identified it. Source explains why: uncommon infected
do not use `z_spawn` at all, but `CreateEntityByName("infected")` +
`SetEntityModel` + `TeleportEntity`, so only the model matters and nothing needs
precaching by the map.

### 3. The commands route through `z_spawn`, and the engine's placement cvars steer them

Line 447 of `all4dead2.sp` is the whole explanation for the observed behaviour:

```c
if (client == 0) {                                    // rcon console
    Format(arguments, sizeof(arguments), "%s %s", type, "auto");
    StripAndExecuteClientCommand(Misc_GetAnyClient(), "z_spawn", arguments);
}
```

It picks an arbitrary connected client and impersonates them. Confirmed live:
setting `z_spawn_const_distance 1200` visibly moved the next spawn further away.

**This is the opening for a `respawn-director` plugin.** The privilege trick is
five lines and needs no `sv_cheats`:

```c
new flags = GetCommandFlags(command);
SetCommandFlags(command, flags & ~FCVAR_CHEAT);
FakeClientCommand(client, "%s %s", command, arguments);
SetCommandFlags(command, flags);
```

An admin-registered command can therefore set `z_spawn_const_pos`/`_distance`,
spawn, and restore — giving **placement as a real argument** while players get
nothing, since `sv_cheats` stays `0`. It could also resurrect `spawn_item`/
`spawn_weapon` by creating and teleporting the entity instead of calling `give`,
the way the uncommon path already does.

### 4. `spawn_*` is instant and local; `force_*` is director-placed and slow

Not wrong in S2, but never stated, and it matters for anything sequencing these.
`a4d_spawn_infected witch` put a witch next to the player immediately (verified —
the player walked into her). `a4d_force_witch 1` only sets `director_force_witch`,
leaving placement and timing to the director, so it needs map progression to
observe. A manifest that presents both as "spawn a witch" will produce
unpredictable pacing.

Also confirmed live: spawning a boss auto-clears its force flag
(`set director_force_witch to 0` fired on the same command), which is the
"prevents four tanks on one map" callback S2 read in source.

### What this follow-up confirmed rather than corrected

- **Cheat cvars are refused over rcon while the plugin's path is not** — S2's
  control finding, re-observed with a live client: `director_no_specials 1` was
  refused with `sv_cheats` at 0, while All4Dead2 set the same class of cvar freely.
- **`a4d_reset_to_defaults` is the safety valve** — restored all six cvars plus the
  director booleans in one call, mid-session, with a player connected.
- **Notifications reach players.** `a4d_enable_notifications 1` then
  `a4d_force_witch 1` put `[A4D] A witch is guaranteed to spawn this round` in the
  player's chat, confirmed by the player. The toggle is real, not inert for
  console-issued commands — which was the open risk, since `NotifyPlayers` is
  called with `client = 0`.

### Verified observable, not merely acknowledged

The distinction the Valheim work established — a reply saying "executed" is not
evidence anything happened — applied here. Confirmed by the player *seeing* the
effect: `force_panic` (a horde), `spawn_infected` (hunter; smoker with
`director_no_specials 1`/`director_no_mobs 1` set, so nothing else could have
produced it; witch), `spawn_uinfected` (clown), `enable_notifications` (chat line),
`reset_to_defaults` (director calmed).

`force_tank` and `force_witch` remain **acknowledged but not observed** — both are
director-scheduled and the session ended before either arrived.
