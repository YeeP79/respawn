# S3 — Does srcds log the rcon password the way HLDS does?

**Status:** ⚠️ Partial — (a) pass, (b) fail with a proven remedy
**Blocking:** No — but it gates go-live, and it is cheap.
**Spawned by:** —
**Needs:** Local docker + an rcon client. No AWS.
**Run by:** Claude (paired)
**Date run:** 2026-08-28
**Commit / branch:** `feat/goldsrc-mod-variants` · image from `lab/s1-modded-image/`

---

## Spec

**Question:** Does the Source dedicated server echo the rcon password to stdout, the way GoldSrc does, putting it into CloudWatch on every MCP call — **and separately, is it exposed in argv?**

**Pass bar:** Two checks, both must pass. (a) Issue at least 5 rcon commands, then grep the full container log for the password — **zero occurrences**. (b) `ps` inside the running container does not show the password in the srcds command line. Any occurrence in either is a fail.

**This decides:** Whether every Source service (`l4d2`, and `css`/`tf2`/`cs2` if they ever enable rcon-control) needs the same stdout redactor the GoldSrc services just got.

**Why this spike exists:** HLDS was measured on 2026-08-28 writing `Rcon: "rcon <challenge> "<password>" <cmd>"` to stdout on every single call, which put the credential in CloudWatch and defeated the point of `SECRET_REFS`. Source rcon is a **different protocol** — TCP with a challenge/auth handshake rather than a password in every packet — so it plausibly does not do this. Plausibly is not measured.

**Widened by S1.** The upstream entrypoint builds `+rcon_password "${RCON_PASSWORD}"` into the srcds
command line, which is exactly what CLAUDE.md's `CONTAINER_COMMAND` gotcha forbids — argv is visible in
`ps` inside the container. That is a second, independent exposure from the logging question, and it is
already known to be true; what this spike must establish is whether it is avoidable (a config file the
entrypoint reads instead) or inherent to the image.

## Prior art

Searched 2026-08-28 — **thin, and that is the finding.**

- The GoldSrc behaviour is **measured, not sourced**: see `apps/_shared/hlds-log-redact.sh` and the CLAUDE.md gotcha it documents.
- [Source RCON Protocol](https://developer.valvesoftware.com/wiki/Source_RCON_Protocol) — **not yet read**. Worth reading first: the protocol authenticates once per connection rather than per command, which is the structural reason to expect a different logging shape.
- No search found anyone reporting srcds leaking rcon passwords to console. That is weak evidence — nobody was looking — and is not a substitute for grepping our own log.

## What was actually done

Two containers, because the two halves need opposite setups.

**For (a), the password was deliberately kept OUT of argv** — supplied only via a
mounted `/cfg/server.cfg` — so that any occurrence in the log would be
attributable to rcon handling rather than to srcds echoing its own command line.
Booted, issued six rcon commands, then grepped stdout and the on-disk game logs.

Then re-tested with the logging the real entrypoint uses (`sv_logecho 1`,
`log on`), and finally forced a map change to generate a large cvar dump, since
that is a plausible leak vector the original bar had not considered.

**For (b), the real entrypoint** with `RCON_PASSWORD` as an env var — the exact
shape a deployed service would take, given `apps/l4d2/.env` maps
`SECRET_REFS=RCON_PASSWORD=…`. Read `/proc/[0-9]*/cmdline` and `/proc/*/environ`
directly rather than using `ps`, which is not installed in the image — and which
is only a `/proc` reader anyway.

---

## Result

### (a) Logging — the password never appears

Zero occurrences of the password across every configuration tried: stdout with
default logging, stdout with `sv_logecho 1` + `log on`, the on-disk game logs,
and after a map change.

**srcds does log rcon activity — without the credential:**

```
L 08/29/2026 - 00:30:39: rcon from "172.17.0.1:55798": command "echo S3MARKER..."
L 08/29/2026 - 00:31:01: rcon from "172.17.0.1:38244": command "changelevel c1m2_streets"
```

Command and source IP, no password. That is a different design from GoldSrc,
which wrote the credential into the equivalent line every time.

**The map-change cvar dump does not carry it either.** 57 cvars are echoed to
stdout on a level change; `rcon_password` is not among them — it is
`FCVAR_PROTECTED`.

**Two measurement traps hit and resolved, both recorded because either would
have produced a confident wrong answer:**

1. A first scan reported `LEAK … /proc/42/cmdline`. Pid 42 was **the grep
   itself** — its own search pattern sat in its own argv. Re-run with
   self-exclusion: clean. The pid was gone by the time it was checked, which is
   how it was identified.
2. The first "zero occurrences" was **ambiguous, not a pass**. A marker test
   (`echo S3MARKER…` over rcon) produced *nothing* on stdout, so the zero could
   equally have meant the log capture was blind. Forcing a map change produced
   **79 lines**, proving stdout works and that the zero is a real absence. The
   rcon audit lines go to the **on-disk log only** and never reach stdout.

### (b) argv — the password is exposed, under the real entrypoint

```
pid 103: /bin/sh ./srcds_run +sv_logecho 1 ... +sv_lan 1 +rcon_password "S3ENVsecret4k2"
pid 106: ./srcds_linux    +sv_logecho 1 ... +sv_lan 1 +rcon_password "S3ENVsecret4k2" -game left4dead2
```

Present in the argv of **both** the wrapper and the server, and in the
environment of pids 1, 103 and 106.

**And it is avoidable.** With the password supplied only through
`/cfg/server.cfg` and `RCON_PASSWORD` unset, rcon authenticates and works
normally while no process argv carries it:

```
./srcds_linux -game left4dead2 -console -norestart -ip 0.0.0.0 -port 27015 \
  +sv_lan 1 +maxplayers 4 +map c1m1_hotel
  → 0 argv entries carry rcon_password
  → rcon still authenticates and executes
```

## Answer

**PARTIAL — (a) passes, (b) fails, and the failure has a proven remedy.**

**(a) srcds does not log the rcon password.** It is not the GoldSrc behaviour and
needs no equivalent of `apps/_shared/hlds-log-redact.sh`. Source authenticates
once per TCP connection rather than carrying the credential in every packet, and
its audit line reflects that: it records the command and the caller's IP.

**(b) The upstream entrypoint puts it in argv**, which is exactly what CLAUDE.md
forbids for `CONTAINER_COMMAND` and for the same reason. Any process in the
container can read `/proc/*/cmdline`. This is a property of the image's
entrypoint, not of srcds — and supplying the password through `server.cfg`
avoids it entirely while leaving rcon fully functional.

The environment exposure (`/proc/*/environ`) is inherent to ECS secrets, which
are delivered as env vars, and is the accepted model across the whole fleet. It
is recorded for completeness, not as a defect.

---

## Consequences

**No redactor is needed for Source.** The GoldSrc wrapper does not need porting,
and no other Source service (`css`, `tf2`, `cs2`) inherits the HLDS problem.
That is a useful negative result — it closes a direction rather than opening one.

**A modded L4D2 service needs a shim, and now for a concrete reason.** It must
read the injected `RCON_PASSWORD`, write it into `/cfg/server.cfg`, and **unset
it before exec'ing the upstream entrypoint** — otherwise the entrypoint's own
`if [ -n "${RCON_PASSWORD}" ]` puts it straight back on the command line. This is
the same `respawn-init.sh` pattern the GoldSrc services already use, and it was
previously justified only by wanting to write config; it is now also a
credential-handling requirement.

**The existing `apps/l4d2` service has this defect today**, in the sense that its
`.env` maps `SECRET_REFS=RCON_PASSWORD=…` straight to the name the entrypoint
consumes. It has never been deployed and `ENABLE_RCON_CONTROL` is unset, so
nothing is currently exposed — but enabling rcon on the stock service without a
shim would expose it.

**One operational note for later:** the `rcon from …` audit lines land in the
on-disk game log and **never reach stdout**, so a deployed service would get no
rcon audit trail in CloudWatch. Not a problem to solve now, but worth knowing
before someone goes looking for one after an incident.

**No spike spawned.** Both halves resolved to definite answers.
