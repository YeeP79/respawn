# S4 — Do joining players need the custom campaign installed?

**Status:** ❌ Fail
**Blocking:** **Yes** — it decides whether campaigns are a knob or their own service.
**Spawned by:** —
**Needs:** A modded server (S1) **and a real L4D2 client that has not subscribed to anything.**
**Run by:** Ryan Hartman
**Date run:** 2026-08-30
**Commit / branch:** `5a351e8` / `main`, image `l4d2-base-spike:s1` (`d4d754b97ac8`)

---

## Spec

**Question:** Can a player who has not subscribed to a custom campaign join a server running it, and play the first map?

**Pass bar:** A client with **no** relevant Workshop subscription and an empty `addons/` connects to a server whose `addons/` holds one custom campaign VPK, and reaches spawn on its first map. Pass = joins and plays. Fail = any missing-content error, a kick, or a map that will not load.

**This decides:** The entire campaigns branch. If clients need nothing, custom campaigns are an image-size problem and a knob. If they must subscribe, campaigns are a separate service with a client ritual, and that ritual is the reason it is separate.

**Why this spike exists:** Two sources that both look authoritative disagree, and the disagreement is not resolvable by reading more carefully — one describes a workflow that never mentions the client, the other describes a failure mode that only exists if the client has its own copy. It is also the cheapest question here to answer definitively and the most expensive to get wrong: building a campaigns service around the wrong answer means either a redundant service or a server nobody can join.

## Prior art

Searched 2026-08-28. **Sources genuinely conflict — this is why it is a spike and not a lookup.**

- [How to make a L4D2 server with mods (2026)](https://moddingcommunity.com/blog/how-to-make-a-l4d2-server-with-mods/) — **read in full.** Walks from dropping VPKs into `addons/` straight to a plain `connect <ip>` and never mentions the client. Confirms servers have **no native Workshop support** and gives the `workshop.py <collection-id>` extraction path. Reads as server-side-only.
- Community sources on custom-campaign servers — **skimmed** — describe a VPK **consistency conflict** between a server copy in `addons/` and a client copy in `addons/workshop/`. That only makes sense if clients hold their own copy.
- Left4DHooks ships an **Addons Manager** (`l4d2_addons_eclipse`: `-1` addonconfig, `0` disable, `1` enable) — **read in the 1.168 thread.** The existence of a server-side switch that force-enables or disables addons suggests client/server addon state is something servers actively negotiate. Unclear which way it cuts.

Nobody found saying plainly "the client does / does not need the file". Do not resolve this by reading harder.

**Verdict on the conflict:** the community sources were right and the walkthrough was
misleading by omission. It never mentions the client because its author already had the
campaign subscribed — the single most likely state for anyone writing such a guide.

## What was actually done

**Subject campaign:** "Time to Die" (Workshop `2257961887`), 4 coop maps, first map
`l4d2_timemachine_01`, 275,385,916 bytes. Chosen because the client had **never**
subscribed to it — see the confound below.

Fetched anonymously, with no Steam account and no subscription:

```
docker run --rm -v "$PWD/lab/s4-campaign/dl:/out" --entrypoint /bin/bash l4d2-base-spike:s1 -c \
  './steamcmd.sh +login anonymous +workshop_download_item 550 2257961887 +quit; \
   cp /home/louis/Steam/steamapps/workshop/content/550/2257961887/*.bin /out/timetodie.vpk'
```

`<id>_legacy.bin` **is** the VPK, byte-identical in size to a subscribed copy (verified
against `210014615`: 90,122,904 bytes both ways).

Server, with the campaign as the only addition to the S1 base image:

```
docker run -d --name s4srv -p 27016:27015/udp -p 27016:27015/tcp \
  -v "$PWD/lab/s4-campaign/dl/timetodie.vpk:/addons/timetodie.vpk:ro" \
  --entrypoint /bin/bash l4d2-base-spike:s1 -c \
  'cd /home/louis/l4d2 && ./srcds_run -game left4dead2 -console -norestart \
   -ip 0.0.0.0 -port 27015 +sv_lan 1 +rcon_password spikepw +maxplayers 4 \
   +sv_allow_lobby_connect_only 0 +map l4d2_timemachine_01 coop'
```

Client: native Linux L4D2, `connect 172.17.0.2:27015`, console captured with `condump`.

**Three method traps had to be cleared first; all three are recorded below because each
one silently produces a wrong answer rather than an error.**

### Trap 1 — Steam restores unsubscribed Workshop files by itself

The first attempt used "Left 4 Mario" (`210014615`), which the client *had* subscribed to,
moving its VPK aside to simulate absence. **Steam re-downloaded the full 90 MB within
minutes, with the game closed**, and did so again after an unsubscribe was attempted.

This is not a nuisance, it is a **false pass generator**: the client would have loaded the
campaign from its own copy and the spike would have recorded "clients need nothing".
Moving files aside is not a valid way to make a client lack a campaign. The only sound
form of this test is a campaign that was **never subscribed**, which is why S4 was re-run
against "Time to Die".

### Trap 2 — `sv_allow_lobby_connect_only` defaults to `1`

A dedicated L4D2 server refuses direct `connect` outright until this is `0`. It must be on
the command line or set over rcon before any client attempt. Noted for S6: this is the
lobby-reservation machinery, and it is a **server cvar, not a client ritual**.

### Trap 3 — `docker-proxy` silently breaks the Source connect handshake

With the standard `-p 27016:27015/udp` publish, the client sent connect packets and got
nothing back — ten retries, four separate attempts:

```
Connecting to public(127.0.0.1:27016)
Sending UDP connect to public IP 127.0.0.1:27016
Retrying public(127.0.0.1:27016)          [x10]
Connection failed after 10 retries.
```

**A2S queries traverse the same published port fine**, which is what made this so
misleading — every server-side health check passed while no client could connect. A2S is
one request/response; the Source connect handshake is stateful across several packets and
`docker-proxy`, a userspace relay that allocates a fresh source port per peer, does not
survive it.

`--network host` is **not** the fix and made things worse: the container's Steam client
collided with the host's running Steam, `SteamAPI_Init` failed, and A2S stopped answering
too — a different failure wearing the same clothes.

The fix is to address the container directly on the bridge, bypassing the relay without
sharing the host namespace:

```
docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' s4srv   # 172.17.0.2
connect 172.17.0.2:27015     # container's own port, NOT the published 27016
```

## Result

**The connection succeeded. The map load did not.**

```
] connect 172.17.0.2:27015
Connecting to public(172.17.0.2:27015)
Sending UDP connect to public IP 172.17.0.2:27015
Server using '<none>' lobbies, requiring pw no, lobby id 0
RememberIPAddressForLobby: lobby 0 from address 172.17.0.2:27015
CSteam3Client::InitiateConnection: 172.17.0.2:27015
Connected to 172.17.0.2:27015

Left 4 Dead 2
Map: l4d2_timemachine_01
Players: 1 (0 bots) / 4 humans
Build: 9309
Server Number: 1

Host_Error: CMapLoadHelper::Init, unable to open maps/l4d2_timemachine_01.bsp
```

The client authenticated, was **admitted as player 1**, received the server's map name and
player count — and then failed on the client-side map load. No kick, no consistency
error, no missing-content dialog. The server accepted a player it could never show a map to.

Server-side content was verified present and correct before and after:

```
Host_NewGame on map l4d2_timemachine_01
SoundEmitter: adding map sound overrides from maps/..._level_sounds.txt
map     : l4d2_timemachine_01
players : 0 humans, 0 bots (4 max) (hibernating) (unreserved)
```

Corroborating cvar evidence — there is no client download path to configure:

```
----- find download -----
"sv_downloadurl" = ""      replicated
 - Location from which clients can download missing files
```

`sv_downloadurl` is the **only** match. `sv_allowdownload` and `sv_allowupload` do not
exist as cvars on this build. `sv_consistency` = `1`.

Client state was verified empty of the subject campaign before the run — no
`timemachine` file anywhere under the L4D2 install, and `2257961887` absent from the six
subscribed IDs.

## Answer

**FAIL, against the pass bar — and the failure is clean rather than marginal.** A client
with no copy of the campaign connects to the server successfully and is admitted as a
player, then dies with `Host_Error: CMapLoadHelper::Init, unable to open
maps/l4d2_timemachine_01.bsp`. It never reaches spawn, so the pass bar ("reaches spawn on
its first map") is not met.

The distinction that matters for the design is **where** it fails. This is not a rejection
at the door — authentication, lobby checks and slot allocation all pass, and the server
reports `Players: 1`. The client simply cannot materialise a map it does not have. The
campaign ships as a VPK addon mounted from the client's *own* `addons/`, and the engine
offers no mechanism to push one: `sv_allowdownload` does not exist on this build, and
`sv_downloadurl` serves loose files, not addon VPKs.

One honest limit on the finding: `sv_downloadurl` was **empty** for this run, so "a FastDL
host serving a loose `.bsp` cannot rescue this" is *not* something this spike measured. It
is the obvious next question and is spawned as S9 rather than assumed either way.

## Consequences

**The campaigns branch is real. Custom campaigns cannot be a knob on the main server.**

Anything shipped in a campaign VPK is invisible to a player who has not installed it, and
the failure mode is bad: the player joins successfully and *then* crashes out with an
engine error naming a `.bsp` path. Nothing tells them to subscribe to anything. Putting a
custom campaign on the shared server therefore breaks it for every player who has not
performed a ritual nobody told them about.

So:

- Custom campaigns get their **own service**, and the client ritual (subscribe on Workshop,
  or install the VPK) is the reason it is separate — exactly the shape the spike was
  written to test for.
- The server-side image cost is now the *lesser* concern. S7 already removed the
  ephemeral-storage blocker; the binding constraint is the client, not the image.
- `SERVICE_DISPLAY_NAME` for any campaign service must carry the requirement, the same way
  `valheim-*` carries its Steam/PC-only exclusion. An invisible prerequisite that presents
  as a crash is precisely the case that rule exists for.

**Spawned:** [S9](S9.md) — can `sv_downloadurl` deliver a custom campaign to a client that
lacks it, and if so at what cost?

**Also worth carrying forward, from the traps above:**

- `sv_allow_lobby_connect_only 0` is required for any direct-connect testing, and is
  evidence for S6 that lobby reservation is server-side and adjustable.
- **Never verify client reachability with A2S alone.** A2S answered on a path where no
  client could connect. Any future "is the server joinable" check must be an actual
  connect, not a query — this applies to the fleet's `IDLE_CHECK_METHOD=a2s` probes too,
  which measure population, not joinability, and were never intended to prove the latter.
- Local spike servers must be addressed on the **container bridge IP**, not a published
  port, whenever a real game client is involved.
